## 1. Общая картина

Задание 1 требует собрать агента **без фреймворка** `openai-agents`: взять только
клиент `openai` и самому написать цикл «модель → вызов инструмента → исполнение →
наблюдение → повтор», с лимитом шагов, обработкой ошибок как наблюдений, журналом
в JSONL и счётчиками токенов. Затем прогнать десять задач, посчитать метрики
pass@1 / pass^k, провести A/B двух вариантов описаний и разобрать три ошибки.

Отличие от практики (ноутбук `week02_agents.ipynb`): там всё делает SDK
(`Agent`, `Runner`, `function_tool`, `SQLiteSession`, гардрейлы). Здесь те же
механики написаны руками поверх `chat.completions`.

Файлы моего кода:

- `agent_loop.py` — инструменты + цикл (ядро задания).
- `check.py` — десять задач и подсчёт метрик.
- `ab_report.py` — A/B описаний и интервал Вильсона.
- `failures.py` — генерация трёх неудачных траекторий.

Данные и функции базы (`sdk_tasks.py`, `poi.sqlite`, `data/`) даны курсом и не менялись.

## 2. Выбор инструментов (задание: 3–5 инструментов)

Я взял **пять** инструментов — минимально достаточный набор, покрывающий все десять
проверочных задач и все типы вопросов:

| Инструмент | Что делает | Обёртка над (sdk_tasks) |
|---|---|---|
| `count_places` | сколько мест вида | `count_places` |
| `find_places` | список мест вида (на улице) | `find_places` |
| `nearest_place` | ближайшее к точке | `nearest` |
| `place_details` | карточка места по id | `details` |
| `top_brands` | частые бренды вида | `top_brands` |

**Почему именно эти.** Задачи делятся на три типа вопросов: «сколько» (счёт),
«какие/где» (список), «что ближе» (расстояние), плюс «какие сети» (бренды) и
карточка места. Пять инструментов закрывают все типы. `top_brands` и `place_details`
нужны, чтобы A/B описаний имел смысл: у них разные области применимости, и модель
должна выбирать между ними по описанию, а не по интуиции.

**Почему не больше.** Лишние инструменты размывают тест выбора: чем больше похожих
инструментов, тем больше шума в A/B. Пять — баланс между покрытием и различностью.

## 3. agent_loop.py — построчный разбор

### 3.1. Цена токенов

```python
PRICE_IN = 13.112    # рублей за миллион входных токенов (polza.ai)
PRICE_OUT = 39.335   # рублей за миллион выходных токенов
```

Тариф провайдера. Числа на порядок отличаются от примерных в `sdk_tasks.py`
(30/120) — здесь реальный прайс выбранной модели.

```python
def cost_rub(in_tokens: int, out_tokens: int) -> float:
    return round(in_tokens / 1e6 * PRICE_IN + out_tokens / 1e6 * PRICE_OUT, 6)
```

Вход и выход стоят по-разному, поэтому цена = сумма двух слагаемых. Деление на
`1e6` переводит токены в миллионы, под которые задан тариф. `round(..., 6)` — чтобы
в отчёте не было мусорных знаков после запятой.

### 3.2. Исполнители инструментов

```python
def _count_places(kind: str, only_24_7: bool = False) -> str:
    return sdk_tasks.count_places(kind, only_24_7)
```

Каждый исполнитель — тонкая обёртка над готовой функцией `sdk_tasks`, которая уже
умеет ходить в SQLite. Важно, что исполнитель возвращает **строку**: строка — это
единственное, что доходит от результата инструмента до модели. Поэтому готовые
функции, которые возвращают словарь (`nearest`, `details`), приходится форматировать
в строку вручную:

```python
def _nearest_place(lat, lon, kind) -> str:
    found = sdk_tasks.nearest(lat, lon, kind, 1)
    if not found:
        return f"мест вида {kind} в базе нет"
    b = found[0]
    return f"{b['name'] or 'без названия'} — {b['distance_m']} м (id={b['id']})"
```

Здесь `nearest` возвращает список словарей; берём первый (`found[0]`), достаём имя,
расстояние и id. В строку кладём и `id` — он понадобится, если дальше модель позовёт
`place_details` (формат результата — такой же интерфейс, как описание, это тема
задачи 2 практики).

### 3.3. Схемы и описания

```python
SCHEMAS = { "count_places": {...}, ... }
```

Схемы — это JSON Schema аргументов каждого инструмента. Они одинаковы для обоих
вариантов A/B (меняется только описание, а не форма). Например:

```python
"count_places": {
    "type": "object",
    "required": ["kind"],
    "properties": {
        "kind": {"type": "string", "description": "вид места латиницей: ..."},
        "only_24_7": {"type": "boolean", "description": "считать только круглосуточные"},
    },
},
```

`required` перечисляет обязательные поля. `description` каждого поля — это то, что
модель видит как подсказку о смысле аргумента.

```python
DESCRIPTIONS = {"short": {...}, "full": {...}}
```

Два варианта описаний одних и тех же инструментов — это и есть A/B. `short` — одна
фраза, `full` — структура «что делает / когда звать / когда НЕ звать / единицы /
пример». Ключевое различие в том, что `full` явно пишет «НЕ зови для X — для этого
есть Y», что должно помочь модели различать `count_places`/`find_places`/
`nearest_place`, когда их роли пересекаются.

```python
def make_tools(variant: str) -> list[dict]:
    descs = DESCRIPTIONS[variant]
    return [{"type": "function", "function": {
        "name": name, "description": descs[name], "parameters": SCHEMAS[name],
    }} for name in EXECUTORS]
```

Собирает список инструментов в формате, который ждёт `chat.completions` (поле
`tools`). Итерируем по `EXECUTORS` — порядок инструментов неважен, важно, что
описание берётся из выбранного варианта.

### 3.4. Цикл run_agent

```python
SYSTEM = ("Ты — городская справочная по Ростову-на-Дону. ...")
```

Системное сообщение: говорит модели, что отвечать нужно по базе и не выдумывать.
Без него модель может отвечать «по памяти» о городе вместо вызова инструментов.

```python
def run_agent(client, model, question, variant, max_steps=6) -> dict:
    tools = make_tools(variant)
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user", "content": question}]
```

Начальное состояние диалога — системная инструкция и вопрос пользователя. Это тот
самый «контекст», который модель видит целиком на каждом шаге.

```python
    trace = {
        "question": question, "variant": variant, "max_steps": max_steps,
        "steps": 0, "tool_calls": [], "final_answer": None,
        "input_tokens": 0, "output_tokens": 0, "error": None,
        "stopped_by_limit": False,
    }
```

`trace` — траектория прогона: всё, что потом уйдёт в JSONL-журнал и в метрики.
`steps` — сколько итераций сделано, `tool_calls` — журнал вызовов, счётчики токенов
начинаются с нуля.

```python
    for step in range(1, max_steps + 1):
        trace["steps"] = step
        resp = client.chat.completions.create(model=model, messages=messages, tools=tools)
```

Главный цикл. Каждая итерация — один вызов модели со всей историей `messages` и
списком `tools`. `range(1, max_steps+1)` — шаги считаем с единицы, последний —
`max_steps`; если цикл дошёл до конца, значит лимит исчерпан.

```python
        if getattr(resp, "usage", None):
            trace["input_tokens"] += resp.usage.prompt_tokens or 0
            trace["output_tokens"] += resp.usage.completion_tokens or 0
```

Копим токены из `usage` каждого ответа. `getattr` с `None` — защита на случай, если
провайдер не вернул `usage` (тогда просто не прибавляем). `or 0` страхует от `None`
внутри полей.

```python
        msg = resp.choices[0].message
        if not msg.tool_calls:
            trace["final_answer"] = msg.content
            return trace
```

Если модель вернула финальный текст (нет `tool_calls`) — прогон завершён, фиксируем
ответ и выходим.

```python
        messages.append({"role": "assistant", "content": msg.content,
                         "tool_calls": [tc.model_dump() for tc in msg.tool_calls]})
```

Иначе модель попросила вызвать инструменты. Добавляем её сообщение в историю —
**вместе с `tool_calls`**. Это обязательное требование протокола: без `tool_calls`
в assistant-сообщении сервер не сопоставит последующие `tool`-сообщения с вызовами.
`tc.model_dump()` сериализует объект вызова в словарь.

```python
        for tc in msg.tool_calls:
            name = tc.function.name
            try:
                args = json.loads(tc.function.arguments or "{}")
            except json.JSONDecodeError:
                args = {}
```

Идём по всем запрошенным вызовам. Аргументы приходят **строкой JSON** — парсим их
в словарь. Если строка битая или пустая — берём пустой словарь, чтобы не упасть.

```python
            try:
                result = EXECUTORS[name](**args)
                err = None
            except Exception as exc:
                result = f"ОШИБКА: {type(exc).__name__}: {exc}"
                err = result
            trace["tool_calls"].append({"name": name, "args": args,
                                        "result": result, "error": err})
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
```

**Здесь ключевой момент задания — ошибки как наблюдения.** Вызов инструмента обёрнут
в `try/except`: если инструмент бросает исключение, цикл не падает, а кладёт в
результат строку `ОШИБКА: <тип>: <текст>` и отдаёт её модели как `tool`-сообщение.
Модель видит ошибку и может исправиться (например, позвать другой инструмент) — это
и есть «ошибки как наблюдения». В обычном (наивном) коде исключение уронило бы весь
прогон. `tool_call_id` обязателен — по нему сервер связывает ответ с конкретным вызовом.

```python
    trace["stopped_by_limit"] = True
    trace["error"] = f"достигнут лимит шагов ({max_steps}) без финального ответа"
    return trace
```

Если цикл прошёл все `max_steps` итераций и ни разу не получил финального текста —
значит модель зациклилась. Помечаем `stopped_by_limit=True`: это и есть предохранитель.
Лимит шагов защищает от бесконечного цикла (и от бесконечного счёта за API).

### 3.5. Журнал

```python
def save_run(trace: dict) -> Path:
    RUNS_DIR.mkdir(exist_ok=True)
    path = RUNS_DIR / f"run_{int(time.time())}.jsonl"
    with path.open("a", encoding="utf-8") as f:
        f.write(json.dumps(trace, ensure_ascii=False) + "\n")
    return path
```

Каждая траектория пишется **одной строкой JSON** в файл. JSONL (JSON Lines) — формат
«одна строка = один объект»: его удобно читать построчно и грепать, не загружая всё
в память. `ensure_ascii=False` сохраняет кириллицу читаемой. Имя файла — timestamp,
чтобы прогоны не перезаписывали друг друга.

## 4. check.py — построчный разбор

### 4.1. Задачи и эталоны

```python
TASKS = [
    ("Сколько в Ростове круглосуточных аптек?", "19"),
    ...
]
```

Десять задач. Каждая — пара `(вопрос, эталон)`. Эталон — строка, которая должна
встретиться в финальном ответе. Эталоны пересчитаны по базе SQLite напрямую,
**без модели**, поэтому проверка объективна.

Как получены эталоны (все запросы к `poi.sqlite`):

- круглосуточных аптек = `COUNT(*) WHERE kind='pharmacy' AND is_24_7=1` = 19;
- всего аптек = 330; супермаркетов = 352; школ = 107; банков = 204; кафе = 261;
- «кафе на Пушкинской» → эталон `Coffee Man` (реальное кафе из `find_places`);
- «ближайшая аптека к 47.2940, 39.8880» → эталон `Апрель` (изолированная аптека, id 1890);
- «ближайшая школа к 47.2690, 39.7170» → эталон `Школа №82` (id 2066);
- «сети пунктов выдачи» → эталон `Ozon` (крупнейшая брендовая сеть, 183 пункта).

Для задач «ближайшая» я намеренно выбрал точки возле **изолированных** объектов
(сосед дальше 800 м), чтобы ответ был однозначным, а у места было название.

```python
def is_solved(final_answer, expected):
    return bool(final_answer) and expected in final_answer
```

Задача решена, если эталонная строка входит в финальный ответ. Проверка по
вхождению, а не по равенству — модель формулирует свободно («19 аптек», «всего 19»),
и важно, что число/имя правильное.

### 4.2. pass@k

```python
def pass_at_k(solved_matrix, k):
    ok = sum(1 for attempts in solved_matrix if any(attempts[:k]))
    return round(ok / len(solved_matrix), 3)
```

`pass@k` — доля задач, решённых хотя бы одной из первых k попыток. `solved_matrix` —
список, где для каждой задачи лежит список булевых результатов попыток.
`any(attempts[:k])` истинно, если хоть одна из первых k попыток успешна.
`pass@1` = доля задач, решённых с первого раза; `pass^3` = доля задач, решённых
хотя бы одной из трёх попыток. Это стандартная метрика надёжности агента.

### 4.3. Интервал Вильсона

```python
def wilson_interval(p, n, z=1.96):
    if n == 0: return 0.0, 1.0
    denom = 1 + z*z/n
    center = (p + z*z/(2*n)) / denom
    radius = z * math.sqrt(p*(1-p)/n + z*z/(4*n*n)) / denom
    return round(max(0.0, center-radius), 4), round(min(1.0, center+radius), 4)
```

Интервал Вильсона — доверительный интервал для доли (биномиальной вероятности),
который, в отличие от наивного «плюс-минус z·√(p(1-p)/n)», не вырождается на краях
(при p=0 или p=1) и даёт корректные границы для малых выборок. Формула берёт
«центр» не в самой точке p, а сдвигает его к 1/2 на величину z²/2n (поправка
непрерывности), затем строит вокруг него радиус. `z=1.96` — квантиль нормального
распределения для 95% уровня. Используется в A/B, чтобы сказать, значимо ли
различие долей, а не просто сравнить два числа.

## 5. ab_report.py — построчный разбор

```python
EXPECTED = {"Сколько в Ростове круглосуточных аптек?": {"tool": "count_places", "args": {...}}, ...}
```

Для каждой задачи заранее задан **правильный инструмент и правильные аргументы**.
Это эталон A/B: метрика — «доля задач, где выбран верный инструмент И верные
аргументы» (не просто «верный ответ», а именно выбор инструмента).

```python
def correct_call(trace):
    exp = EXPECTED.get(trace["question"])
    if exp is None: return False
    calls = trace.get("tool_calls") or []
    if not calls: return False
    first = calls[0]
    if first.get("name") != exp["tool"]: return False
    got_args = first.get("args") or {}
    for key, want in exp["args"].items():
        got = got_args.get(key)
        if key == "street":
            if not got or str(want).lower() not in str(got).lower(): return False
        elif got != want: return False
    return True
```

Проверяем **первый** вызов инструмента: совпало ли имя, затем каждый ключевой
аргумент. Для `street` сравнение по вхождению (модель может написать «Пушкинская»
вместо «Пушкин»), для остальных — строгое равенство. Это отражает реальную задачу
выбора инструмента: агент должен с первого шага позвать правильный инструмент с
правильными аргументами.

В `main` для каждого варианта считаются доля, интервал Вильсона и средние токены, а
затем — вывод, окупились ли лишние токены полных описаний.

## 6. Результаты и их смысл

- **pass@1 = pass^3 = 1.0** на десяти задачах для обоих вариантов: на этих простых
  справочных задачах модель безошибочна.
- **A/B**: 30/30 у обоих вариантов, интервал Вильсона [0.887, 1.000]. Вывод —
  полные описания не окупаются (на ~1030 входных токенов дороже на прогон, а точность
  та же). Это честный отрицательный результат: на простых, хорошо различимых
  инструментах короткие описания достаточны.
- **Стоимость**: прогон стоит ~0.04–0.13 ₽ на задачу — реальный прайс polza.ai.

## 7. Три класса ошибок (failures.py)

Штатные задачи пройдены без провалов, поэтому неудачные траектории получены
намеренно — по одному на класс:

1. **Ошибка среды** (`broken_divide` делит на ноль). Цикл поймал `ZeroDivisionError`,
   отдал модели `ОШИБКА: ZeroDivisionError: division by zero`, модель не упала и
   корректно вышла из ситуации. Демонстрирует пункт задания «инструмент бросает
   исключение — цикл падает вместо того, чтобы дать модели шанс исправиться».

2. **Зацикливание** (`stubborn` вечно просит уточнить). Модель звала инструмент до
   исчерпания `max_steps=6`, прогон остановлен `stopped_by_limit=True`. Демонстрирует
   предохранитель и то, зачем он нужен.

3. **Ложное «готово»** (вопрос «где лучше открыть кофейню»). Модель позвала
   инструменты, но в ответе выдала рекомендации, не проверяемые по базе (аренда,
   трафик, «лучшее место»). Демонстрирует ограничение схемы: форма ответа — не
   гарантия правды.

2. `practice/check.py` — задачи, эталоны, pass@k, интервал Вильсона.
3. `practice/ab_report.py` — проверка верного выбора инструмента.
4. `practice/failures.py` — три сценария ошибок.
5. `week1/setup.md` — зачем `uv`, `.env`, агент.
6. `week2/practice/README.md` — устройство практики (11 задач на SDK).
7. `week2/practice/week02_agents.ipynb` — как то же самое делает SDK (для контраста).
8. `week2/assignment.md` — полное условие задания 1 и рубрика.

Ключевые понятия, которые могут спросить:

- что такое `tool_calls` и почему вызов инструмента — это участок ответа, а не действие;
- почему формат результата инструмента — такой же интерфейс, как описание;
- зачем `max_steps` (предохранитель от бесконечного цикла и счёта);
- почему исключение инструмента нужно превращать в наблюдение, а не ронять цикл;
- что такое pass@k и чем интервал Вильсона лучше наивного доверительного интервала;
- что даёт схема (enum, типы) в отличие от свободной строки;
- почему A/B сравнивает именно «верный инструмент и аргументы», а не итоговый ответ.
